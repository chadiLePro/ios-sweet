## Samsung boot and Download Mode constraints

[Samsung documents hardware-rooted boot verification and rollback restrictions](https://docs.samsungknox.com/admin/fundamentals/whitepaper/samsung-knox-mobile-security/system-security/hw-backed-security/).
[Lineage's device installation procedure](https://lineageos.github.io/lineage_wiki/devices/a52q/install/)
uses Download Mode and partition flashing, not Xiaomi's temporary fastboot boot.
Generic chain supported by these sources and captures: ROM-rooted verified
Samsung/Qualcomm firmware -> Android boot loader/security policy -> v2 image
with DTB/DTBO -> kernel. Exact closed-firmware stage behavior and EL1 handoff
have not been traced here. The kernel entry uses the
[Linux arm64 Image contract](https://docs.kernel.org/arch/arm64/booting.html).

No Samsung temporary RAM-boot transport is verified. Recovery fastbootd, if a
different recovery provides it, does not establish bootloader `fastboot boot`.
Do not run the README's fastboot userdata/root/log commands on this phone.
Unlocked status does not establish that every unsigned image or downgrade is
accepted; Samsung policy and rollback checks still require attention. Existing
custom firmware is evidence of custom boot support, not proof this image boots.

## Implementation and local reproduction

`devices/a52q.json` is a separate target description. Runtime XNU addresses stay
unset. `shim/a52q/` is isolated from the Redmi shim. It masks interrupts, handles
EL1 or EL2 with MMU off without changing privilege, installs the active EL's trap capture, records CPU feature registers and
CNTFRQ, then parks. No UFS, USB, GIC programming, SMP, payload loading or filesystem
code is linked. Optional ramoops output is generated from captured evidence;
default builds only record in the image's own RAM. Other ELs or MMU-on entry park
without output. A RAM-log access fault stops further output and parks.

```sh
python3 tools/a52q_collect.py --adb /path/to/adb
python3 tools/a52q_inspect.py backup/a52q/CAPTURE --out backup/a52q/CAPTURE/report.json
python3 -m unittest discover -s tests -v
gcc -std=c11 -Wall -Wextra -Werror tests/host_ramlog_test.c -o /tmp/ramlog-test
/tmp/ramlog-test
python3 tools/build_a52q_diag.py --evidence backup/a52q/CAPTURE --out shim/out/a52q-ramoops
python3 tools/package_a52q_diag.py --evidence backup/a52q/CAPTURE \
  --build shim/out/a52q-ramoops --mkbootimg /path/to/pinned/mkbootimg.py \
  --out shim/out/a52q-ramoops/a52q-diag-UNTESTED-unsigned-full-r3.img
python3 tools/qemu_a52q_diag.py --build shim/out/a52q-ramoops \
  --out shim/out/qemu-diag-test --linux-entry --entry-el2
```

Builder accepts `--cross-prefix`; Windows used native Arm GNU 14.3.Rel1
`aarch64-none-elf-` with the repository's freestanding flags. Toolchain ZIP SHA256
`11fb04ba261d194f44b26b58c970427c7c372d54c8846fca0af9e4f62df96738`.
AOSP mkbootimg is pinned to `android-11.0.0_r48`, script SHA256
`5579fb6bcb9e89e790a70fb9ccf3c00cf56e3e46aef74d84fcb0964887e5576e`.
External tools are under ignored `research/toolchains/`, not vendored.
The added CI workflow builds a no-output core and runs host/QEMU checks; it has not
been dispatched and no cloud CI results are claimed.

Package checks v2 geometry, matching DTBO board/ramoops, existing vbmeta policy,
and build/evidence binding. It retains original ramdisk/DTB and boot-header fields,
preserves the observed `SEANDROIDENFORCE`+NUL trailer, verifies the extracted gzip
kernel, recomputes the AOSP boot-image ID, and zero-pads to the full observed BOOT partition
size so a partial write cannot leave the original AVB footer at the tail.
It is unsigned; no signature validity is claimed.

### Conservative RAM planning

`tools/a52q_memory.py` intersects enabled root FDT banks with captured Linux
`System RAM`. It removes FDT memreserve entries, static reserved-memory nodes,
all non-RAM iomem mappings (including nested kernel code/data), and optional
explicit runtime exclusions. For dynamic reserved-memory nodes it excludes the
**entire alloc-ranges window**, rather than guessing the allocation's location
from its size. Missing allocation bounds, translated reserved-memory addresses,
redacted iomem and inconsistent banks block the calculation. This follows the
[reserved-memory binding](https://github.com/devicetree-org/dt-schema/blob/main/dtschema/schemas/reserved-memory/reserved-memory.yaml).

Reproduce privately:

```sh
python3 tools/a52q_memory.py backup/a52q/20261111T100325Z \
  --out backup/a52q/20261111T100325Z/memory-plan.json
```

For this capture the only remaining 16 KiB aligned snapshot candidate is
`[0x105900000, 0x200000000)`. The Redmi default placement at `0x100000000`
is rejected because it intersects Samsung's debug reservation. A CLI placement
check (`--check-base`, `--check-size`) must fit entirely within one candidate.
`--exclude BASE:SIZE` adds occupied live image/DTB/initrd/stack/payload ranges.

This is **not an approved XNU RAM interval**: firmware/XPU permissions, ownership
at actual handoff, and mapped reads/writes remain untested. No address is chosen
automatically, no image is generated and no RAM or device partition is touched.
Private input hashes accompany the report. Synthetic tests cover reservation
holes, dynamic bounds, overflow, translation, redaction and page alignment.
The memory-planner commit `a317b56` passed [diagnostic CI with 52 unit tests,
cross-compilation and four QEMU cases](https://github.com/chadiLePro/ios-sweet/actions/runs/43013452142).

## Next hardware test: scope, data loss, and recovery (not executed)

Do not flash until the candidate and this procedure have been reviewed and the
user explicitly authorizes the particular test. The upstream AGENTS/NOTES
Xiaomi userdata approval belongs to another device/session and does not apply.

Proposed test changes **BOOT only**, currently `/dev/block/sda19`, 100663296
bytes. It replaces the normal Android kernel until restored. It does not target
RECOVERY (`sda20`), DTBO (`sda21`), VBMETA (`sde20`), USERDATA (`sda31`), EFS,
modem, bootloader or partition tables. The diagnostic writes only its own RAM
and the reserved ramoops console; it overwrites that previous RAM console record.
No userdata format is part of this test; do not accept a factory reset prompt.
Loss of Android bootability until BOOT restoration is expected. Hardware or
loader failures can still prevent recovery. Samsung Knox state can be irreversible;
restoring a boot image does not restore a blown warranty bit.

Before the test, put the exact original BOOT backup and its hash on accessible
external media/USB OTG and retain the host copy. Confirm TWRP remains independently
bootable and retain its backup. Original BOOT SHA256:
`d6bf03071b0c49bb554effdc62f49014719efe9dcce8922af9c1082c1cc4b016`.

After a separately approved BOOT-only install, expect a stationary boot splash
or blank screen, not a GUI. Force restart using Volume Down + Power for about
8-10 seconds; on black screen immediately use Volume Up + Power with USB connected
to enter existing TWRP. Read `/sys/fs/pstore/console-ramoops-0` immediately over

reviewed recovery plan with correct SM-A525F firmware and an acceptable rollback
revision. That fallback is not a tested recovery guarantee; do not experiment with
bootloader partitions, PIT/repartitioning or downgrade images.

MMU/D-cache off and x0 pointing to revision-2 boot_args.
